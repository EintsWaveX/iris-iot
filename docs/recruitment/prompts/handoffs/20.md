## What changed
1. **`sinkronKursi` and a running part** (`recruitment-room.ts`, `recruitment-slots.ts`). It now reads the seat's current room and the room it would move to and leaves the seat alone when either has a part running, using the same four views as `room-move` (`part-running`, `livecode-running`, `part-paused`, `part-ended`; now one helper, `ruangBerjalan`, which `pindahKursi` uses too). This covers the drop path as well (a candidate taken out of the evening while the room runs keeps even an untouched seat). It returns `{ tetap }`. The five callers (pick, decided request, Plotting move, Auto Isi, its Urungkan) put the candidate ids that stayed in the audit line and in the response as `kursiTetap`, so Panitia see it and use `room-move` once the room is between parts. A pick (the candidate's own call) only audits it. Tests: approving a request mid-evening leaves the seat (both directions: own room running, target room running), plus the unit cases.
2. **Kumpulkan** (`seat-answers.ts`, `Runner.tsx`, `testStrings.ts`). Drains are now serialised, so a `flush` runs after any send already in flight. Each question's value is read at the moment it is sent, so a question changed while another was flying goes out new. `flush()` returns `true` when nothing is left unsent and `false` while an answer could not go out (offline); `handIn` stops, clears the busy state and toasts a new `handIn.unsent` line (id, en, zh) instead of handing in. An answer the server refused (time over) is dropped and does not block, as before. Tested as a pure unit with a controllable `send`: newer value re-sent after the in-flight one returns, mixed questions, offline gives false, clean and refused give true.
3. **Kejadian** (`recruitment-seat.ts`). A client id starting `ganda-` is refused (`data_salah`), the prefix is now one constant used for the server-made ids too. An existing kejadian can only grow: kinds are the union of what is stored and what arrives, `backAt` is set once (`coalesce` in SQL; the update does not touch it when the page sends none), `at` is never rewritten. The first write is `ON CONFLICT DO NOTHING`; if another request of the same page won the race the call falls through to the extension path. The pengawas feed carries the merged record. Tested through the handler.
4. **Practice-room token** (`recruitment-lc-common.ts`). New pure `kedaluwarsaToken(room, slot, now)`. A real room is unchanged (slot end + 8 h). A practice room gets the start of the current UTC day + 32 h: at least 8 h left at any moment, and it changes only at midnight, so the header (which carries the token) does not go stale between compiles. A header compiled yesterday shows stale today, which asks for one recompile. Alternatives I rejected: issue time (changes on every page load and makes every header stale) and the room's `startedAt` (unknown before the room starts, which is when boards are compiled).
5. **Grading list** (`lc-grade.ts`, `recruitment-lc-grade.ts`, `lc-api.ts`, `GradeTab.tsx`). `runTerakhir(runs, kind)` picks the newest by time and counts; the row shows `OK 21.40 (3x)` when there is more than one. `lastCompile` and `lastFlash` gained `n`.
6. **Extra time on an ended part (`room.ts:378`): not fixed, no one-line fix.** After `seat-time` on an ended part, `durMs = min(durMs, usedMs)` and `mark = now`, so every other seat's end is `now` and `answerOpen` lets all seats write until `now + GRACE_MS` (5 s). The right fix moves `mark` back by `GRACE_MS + 1` and adds the same to the extra seat's `extra`, so the extra seat still ends at exactly `now + delta` and the others' end falls behind `now - GRACE_MS`. That is two edits in the room-clock accounting (`clock`, `normalize`'s `endedAt`, `seat-time`'s lobby test) and I did not want to change it without the rig. The effect is bounded: 5 s, on a part that just ended, only after a Master pressed seat-time. Suggest doing it with the next room-clock change and adding the test "other seats are closed the instant a seat is rerun".

## Not for me: my view, nothing changed
- **`ganda` is easy to avoid.** A duplicated tab copies `sessionStorage`, so `TAB` repeats and no second tab id is ever seen; a second reader device on the same login is never flagged unless it also answers; `masuk` never checks for another tab, though EXAM-ENGINE says check-ins count. Options: (a) a server-issued tab nonce at `masuk`, stored on the seat, sent with every call, and a second `masuk` or a mismatched nonce flags `ganda` at once (my pick: it catches duplicated tabs and second devices, costs one column or a field in `checkin` and a header on the seat calls); (b) count distinct tab ids seen on `GET test` as well as on writes (cheap, still misses a duplicated tab); (c) accept it as a deterrent only and say so in the rules. It is a strike, not a block, so false negatives cost less than false positives; if you pick (a), have the new tab take over and the old one show the existing cover.
- **Cleartext on port 80 over shared hotspots.** The gateway token (in the WS and HTTP paths) and the MQTT user and password in the header travel over plain ws/http on a phone hotspot anyone in the room may be near, and every candidate's sketch holds the pengawas hotspot SSID and password (`IRIS_WIFI_PASS`), so each candidate can join the fallback hotspot and see the others' traffic. This is a limit of the agreed gateway (boards cannot do TLS cheaply; ruling 2026-10-24). Mitigations, cheapest first: have candidates use their own phone hotspot (already allowed) and keep the pengawas hotspot only as the fallback; give the fallback hotspot a different password each evening (a Panitia setting, not a code change); keep the token's reach small (it is per seat and already expires at the evening's end + 8 h, or the day of use for practice); each seat already has its own MQTT account (`akunMqtt`); if the broker also limits that account to the seat's `rec/<seat>/` topics (I did not check the broker side here), a stolen MQTT password is one seat, and if it does not, that is worth adding; ask the pengawas to watch for a candidate whose board talks to the wrong seat id; wss/https on the gateway if a board library with TLS is ever accepted (more RAM, slower connect).
- **Board evidence is self-reported.** `ble` lines come from the candidate's page (`rec.ts` `m.t === "ble"`) and a flash result comes from the candidate's page too (`flash` in `recruitment-lc-compile.ts`), so "the board talked BLE" and "flash ok" are what the candidate's browser says. Graders should treat them as hints and look at the board and the live traffic lines (those arrive from the gateway side for ws/http/mqtt). A note on the Penilaian screen would be enough.
