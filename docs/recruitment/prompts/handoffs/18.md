## What changed
1. **Seat sync.** `sinkronKursi` (`recruitment-room.ts`) is now called, inside the same transaction as the assignment write, from the slot-set move (`handleAtur`, including `toSlot: null`), Auto Isi and its Urungkan (`handleIsiOtomatis`), an approved slot request (`handleKeputusan`) and a pick (`handlePilih`), tes_tulis only. 06's three handlers were the ones the 11 handoff said it touched; none of that had survived into the tree.
   - **Behaviour for "no room":** `rec_exam_seat.room_id` is `NOT NULL`, so a seat cannot be left room-less without a migration. The function now drops a seat that never drew, handed in or struck (check-in makes it again) and keeps one that did, in the room it was in, so the draw is never lost and Susulan can still use it. The old code did nothing in both cases. Your prompt said "dropped, with its draw kept"; that is the closest reading the schema allows. If you want a drawn seat to leave its old room too, that is a migration (`room_id` nullable) and a pass over every reader.
   - Not pushed to the relay: the seat's old room is not told it lost a seat; the console shows it on its next load. `room-move` (`pindahKursi`) already moves the seat itself and tells the relay.
2. **Finalkan on a partial cohort.** Two new blockers, `slot_tanpa_ruang {slots}` (a tes_tulis evening with candidates and no real room) and `peserta_tanpa_kursi {candidates}` (plotted to an evening, no seat). Candidates `withdrawn` or `out` are not waited for. Shown in the Penilaian tab in id, en and zh.
   - **Consequence to decide on:** a candidate who is plotted and simply never shows has no seat, so Finalkan stays blocked until Panitia moves them out of the evening or marks them `out`/`withdrawn`. That is what the prompt asked for; there is no "mark absent" button that settles it from the Penilaian tab. Say if you want one.
3. **Freeze vs Live Coding grades, and atomic checks.**
   - `lc-grade` and `lc-grade-withdraw` refuse `nilai_final` while frozen and write `rec_lc_nilai` / `rec_lc_nilai_tarik` audit lines. `canSubmit` now runs on the sheets read under the lock, so two third graders cannot both pass.
   - `denganKunciNilai(db, edisiId, fn)` (`recruitment-score.ts`): a transaction that takes `pg_advisory_xact_lock(7102, editionId)` first, then runs `fn`. The freeze is read inside it, after the lock. Used by Finalkan (check, compute, blockers and the insert), void/unvoid, both sheet actions, `question-save` on a dealt question and a real `bank-import`. I used an advisory lock rather than the edition row because a freeze is an INSERT (there is no row to lock when none exists) and `FOR UPDATE` on `rec_edition` would block unrelated inserts that reference it. The code base already uses `pg_advisory_xact_lock` (`retensi.ts`, `tangkapan.ts`, `tp-unggah.ts`).
   - **What the test proves, and what it does not:** the fakes record the order the database is asked (lock, freeze read, write) and the tests fail without the lock. A real two-connection race was not run (no rig Postgres here). Run `rec_score_api.mjs` on the rig, plus a two-terminal void against Finalkan, before shipping. The partial unique index `rec_score_freeze_hidup` stays as the last word.
   - Finalkan now computes under the lock inside one transaction; it holds the lock for the length of one scores computation (30 seats: milliseconds).
4. **Rehearsal draws and delete.** `hapusSoal` answers `sudah_tampil` when `shownAt` is set, or any `rec_answer` row, or any seat's draw in the edition names the question; a `23503` at the delete itself also answers `sudah_tampil`. The draw scan reads the edition's seats' `draw` column and checks in code (hundreds of rows at most).

## Left for you, with my view
- **The cut lock and the freeze** (`recruitment-cutting.ts handleKunci`, `recruitment-score.ts bukaBeku`): Cutting a Tes Tulis can be locked on provisional totals, and a freeze can be opened after the cut was revealed. My view: lock should require a freeze for tes_tulis, and unfreeze should refuse once a cut for that stage is revealed (a revealed result is a promise to candidates). Not changed; it is your call and it needs a copy decision for the refusal.
- **A seat answer after Kumpulkan** (`recruitment-seat.ts jawab`): `seat.done` is read before the upsert, so an answer sent in the same millisecond as a hand-in can land after it. Real but tiny window; the fix is a conditional upsert on `done` in SQL. I would fix it with the next seat change, not alone.
- **`aturRuang` merges hotspots without `FOR UPDATE`** (`recruitment-room.ts`): a candidate saving their phone while Panitia edit the room's hotspots can lose one write. `simpanHotspotKursi` and the seat's clear already lock; `aturRuang` should lock the room row at the start of its transaction and re-read `hotspots` there. A short change, but it moves code in a transaction I did not want to touch blind. Worth doing before the first real evening.
- **`rec_exam_room.slot_id` cascade:** deleting a slot deletes its room (`ON DELETE CASCADE`), and the room's logs, notes, loans go with it, while `rec_exam_seat.room_id` has no cascade, so the slot delete fails with a 500 if a seat exists. `slot-set delete` already refuses a slot with assignments (`slot_terisi`), which covers it in practice (a seat implies an assignment unless fix 1's null path ran). My view: leave the cascade, and make `slot-set delete` also refuse when a room has seats.
- **Upload `checkUrl`** (`recruitment-snapshot.ts`): not changed. The review found no SSRF hole; the open point is only that `checkUrl` is applied to the redirect target by hand at one site. Reading it again I would leave it and add a test that every redirect hop goes through `checkUrl`.
- **Seats of a deleted-untouched sync:** if a plotted candidate with a drawn seat is moved to an evening with no room, the seat stays in the old room until Panitia use `room-move`; `muatKursiSendiri` then shows them the old room. If you want the drawn seat to follow the moment the new evening's room is created, `aturRuang` can sync seats of that slot's candidates on create. Not done.
